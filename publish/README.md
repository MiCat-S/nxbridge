# nxbridge

nxbridge 让同一台电脑上的 Claude Code 和 Codex CLI 互相发消息，像两个平等的同事一样协作。两边仍然是各自的官方 CLI，各有自己的上下文和权限。

nxbridge 不调用其他模型，不会替你回答审批，也不会把一边变成另一边的子代理。

## 一分钟了解

**最常见的用法：** 在项目目录里只打开 Claude Code，让它“交给 Codex 做”。nxbridge 会在后台启动一个 Codex 当搭档，两边互相发消息、分工合作；你只和 Claude 说话，想看 Codex 在做什么时运行 `nxbridge open codex`。

**由哪几部分组成：**

| 部分 | 作用 |
|---|---|
| 两边的插件 | 安装时用两家官方的插件命令装进 Claude Code 和 Codex，提供发信工具、状态栏和提醒 |
| 本机协调器 | 一个后台进程，保存消息、配对和双方状态（`~/.nxbridge`），负责投递、叫醒、掉线恢复和异常提醒 |
| `nxbridge` 命令 | 安装、查看状态、诊断和手动处理，见“常用命令” |

**几个基本概念：**

- **配对：** 一个 Claude 窗口和一个 Codex 会话结成 1:1 的搭档，一台电脑上可以同时有多组，互不干扰。第一次发信时配对：同目录有你开着、还没有搭档的窗口时先问你，没有就直接启动后台搭档。
- **后台搭档：** 你没有自己打开的那一边，由 nxbridge 在后台启动。它收到消息会被叫醒干活，崩溃后自动按原会话恢复。你自己打开的窗口则不会被主动叫醒、关闭或接管。
- **消息：** 每条消息都有编号、送达状态和回复关联，保存在本机。送没送到会如实告诉发信方；结果不明的消息不会自动重发。
- **提醒：** 发现送不到、长时间没进展、模型服务出错等情况时，只陈述事实，交给相关的一方或你判断，不替谁做决定。

**AI 怎么用它：**

- Claude 用原生 `SendMessage` 发给 `nxbridge:codex`，用 `ListAgents` 查看搭档；Codex 用 `claude.send_message` 发信、`claude.status` 查看搭档。
- 两边的分工和沟通规则由插件自动注入，用户不用另外交代。
- 以 `nxbridge runtime monitor` 或 `nxbridge system_notice` 开头的内容是 nxbridge 发出的事实提醒，不是用户的话，也不是搭档的回复。
- 诊断时先用 `nxbridge doctor --current`（只看本窗口的配对）或 `nxbridge status`。
- 信任 hooks、改配置里的敏感项、给别的窗口重新加载插件、在用户自己的窗口里批准操作等，只有用户能做：AI 只告诉用户具体步骤。

## 需要什么

- Node.js 24～26（需要内置的 `node:sqlite`）。
- 已登录的 Claude Code 和 Codex CLI。已测试的版本是 Claude Code 2.1.308、2.1.316 和 2.1.317，Codex 0.164.0 和 0.166.0。
- 两家 CLI 比上面的版本旧时，安装检查会提示，但不一定不能用；能升级的话建议先升级。
- Codex 不管通过 WebSocket 还是 HTTP 连接模型服务（包括自定义中转），都能正常收到消息。
- 已在 Windows 和 WSL（Ubuntu-22.04）上验收过。其他 Linux 发行版应该可以用，但没有单独测过。
- **macOS 只在真机上验证过一部分。** 2026-11-12 一位 Mac 用户实测通过了两项：转到后台时选对 Codex 程序；自己开的 Codex 窗口空闲时能被叫醒。这一版按实测反馈又修了几处，只做了模拟测试，没有在 Mac 上跑过：
  - nxbridge 自己启动的后台 Codex 解除配对后停不掉；
  - 手改配置文件后要运行 `reload` 才生效；
  - 重新打开窗口后不会自动收信。

  其余流程也没有在 Mac 上完整跑过。建议先运行 `--dry-run`，遇到问题请把完整输出反馈给作者。

## 安装

在这个文件夹里打开终端，执行：

```sh
node nxbridge.mjs setup
```

安装前会先检查环境。有任何一项不满足，它不会写入任何东西，而是告诉你原因。

- 只想先看看会做什么，可以加 `--dry-run`：它做的检查和正式安装完全一样，但不写入任何东西。
- `--help` 只显示帮助。`setup` 和 `update` 遇到不认识的参数或缺少参数值时，会在做任何事之前报错。
- 安装或更新中途被打断（比如进程被杀、文件被占用）时，再运行一次同样的命令就会接着完成。

安装会做这些事：

- 把运行文件复制到 `~/.nxbridge`。装好后，这个文件夹就可以删掉了。
- 用两家官方的插件命令安装 nxbridge 插件。
- 在 PATH 里找一个你自己可写的目录（优先 `~/.local/bin`、`~/bin`），放一个 `nxbridge` 命令，不需要管理员权限，也不改 PATH。找不到合适目录时，会给出可以直接运行的完整命令，后面文档里的 `nxbridge` 都换成那条命令即可。

它不会改你的模型、审批、沙箱设置，不装系统服务，也不改 shell 配置文件。nxbridge 在后台启动的搭档用什么权限，只通过那一次启动的参数决定，不写进你的配置，见“后台搭档全自动运行”。

## 装好后还要手动做的事

1. **Claude Code：** 在已经打开的窗口里执行 `/reload-plugins`，或者新开一个窗口。
2. **Codex：** 新开一个会话，然后在 `/hooks` 里信任 nxbridge 的 hooks。nxbridge 不会替你信任。
3. **登录和目录信任：** 两边的登录和项目目录信任，需要先在各自的界面里完成。没完成的话，后台会话可能会停下来等你处理。
4. **权限模式：** 想让 nxbridge 在后台启动的 Claude 全自动运行，需要你先在任意终端运行一次 `claude --dangerously-skip-permissions` 并接受提示（只需一次，见“后台搭档全自动运行”）。两边都是你自己开的窗口时，让两边的权限模式属于同一类，见“让两边的权限模式属于同一类”。
5. **检查：** 运行 `nxbridge doctor`，见“检查安装”。

### 后台搭档全自动运行

nxbridge 在后台启动的搭档（你没有自己打开的那一边）默认全自动运行，不需要你批准操作，这样配对可以长时间无人值守地工作。权限只通过这一次启动的参数设置，不改你的 Claude 或 Codex 配置；你自己打开的窗口、你接手或交还过的会话、已经在运行的会话都不受影响。

- **后台 Codex：** 你的 Claude 是全部放行时，后台 Codex 也以全部放行启动；你的 Claude 是需要确认的模式时，后台 Codex 用 Codex 自带的自动审查：需要批准的操作由 Codex 的审查模型代你判断，不弹出审批，两边仍属于同一类。启动后 nxbridge 会核对实际生效的设置，再让它开始干活；如果这个版本的 Codex 不支持或忽略了自动审查，就在开始任何工作之前改用全部放行，这时两边类别不同，Codex 发来的消息可能被你的 Claude 拦下审核，状态栏会说明。
- **后台 Claude：** 以全部放行启动。如果你的 Codex 是需要确认的模式，或者判断不出它属于哪一类，还会只对这个后台 Claude 打开“接收其他会话的消息”，否则 Codex 的消息会被拦下等审核，而后台会话没人能审核。注意：这等于让一个需要确认模式的 Codex 指挥一个全部放行的 Claude 干活，Claude 原本的这道隔离不再起作用；而且这个后台 Claude 会接收本机任何会话发来的消息（Claude 没有只放行某一个会话的设置）。
- **一次性前提：** Claude 规定，后台以全部放行启动之前，必须由你本人确认过一次全部放行的风险提示，确认结果只认你的用户设置，启动参数替代不了，nxbridge 也不会替你写入。还没确认过时，nxbridge 不会启动后台 Claude，也不会改用需要人批准的模式凑合，而是先保留消息，并在发信结果、`nxbridge doctor`、安装或更新的结果里提示你：在任意终端运行一次 `claude --dangerously-skip-permissions`，接受提示后退出。之后再发信就会正常启动。
- **Linux / WSL 上以 root 身份运行：** Claude 出于安全考虑不允许 root 用户使用全部放行模式，所以以 root 运行时，nxbridge 不能启动全自动的后台 Claude，会保留消息并说明原因，不会改用需要人批准的模式凑合。请改用普通用户运行。
- **管理员禁用了全部放行：** 如果组织的托管设置禁用了全部放行模式，后台 Claude 无法全自动运行，这一步只能由管理员处理，状态会写明原因。
- **接收设置被更严格的设置覆盖：** 组织的托管设置或项目设置把“接收其他会话的消息”设成暂扣或拒收时，启动参数里的设置不生效。Claude 状态栏和 `nxbridge status` 会写明是哪一层设置挡住的。

### 让两边的权限模式属于同一类

Claude Code 会拦下“权限模式类别不同”的会话发来的消息，等你逐条审核。权限模式分两类：

- **全部放行：** bypass，计划模式也算这一类。
- **需要确认：** 默认、自动（auto）或自动接受编辑等模式。

一边是全部放行、另一边是需要确认的模式时，消息就会被拦。被拦的消息在审核框里默认约 5 分钟不处理就会作废，没有送达。nxbridge 不会替你绕过这项检查，但会尽量让你知道：

- **配对时：** 一配上就提示 Codex 的回信会被拦下，Claude 也会当场告诉你。远程连接时你可能看不到状态栏和审核框，这一步尤其重要。
- **有消息被拦着时：** Claude 状态栏写明有几条在等你审核。
- **消息作废后：** 状态栏写明有几条没被放行、已经作废（30 分钟内显示），并告诉发信的一方消息没送到；结果不明的不会自动重发。

处理方法任选其一：

- 把两边切到同一类模式（推荐）。两边都不用全部放行模式也能正常通信，这是推荐的用法。
- 每次在 Claude 里展开被拦的消息，确认来自 `nxbridge:codex` 后放行。不想让审核框到期丢消息，可以在 Claude 设置里把 `dialogExpiry` 设为 `never`。
- 在 Claude 的 `/config` 里允许接收其他会话的消息（即设置 `crossSessionInbound` 为 `accept`）。注意这会放行所有会话发来的消息，不只是 nxbridge 的。

nxbridge 怎么判断类别、怎么提醒：

- nxbridge 按 Codex 实际生效的审批和沙箱设置判断它属于哪一类，不只看 hooks 报告的模式。
- nxbridge 会按这一组配对两边的实际类别提醒你：类别不同时，配对选择框和 Claude 状态栏会直接写出能做的一步操作，比如在本窗口按 Shift+Tab 切到普通模式，或让 Codex 不用全部放行模式运行；类别相同时不提醒。
- 暂时判断不出 Codex 属于哪一类时，消息照常发出、不标类别：普通模式的 Claude 会照常收到，全部放行类的 Claude 可能拦下等你审核，状态栏会说明。
- `nxbridge restart codex` 会沿用会话原来的审批和沙箱设置；改了 `~/.codex/config.toml` 里的这两项后，要新开会话才会生效。
- 本版之前已经在后台运行、用自动模式启动的 Claude 照旧：如果你用的 API 网关不转发自动模式的安全检查，它第一次因此拒绝操作后，nxbridge 会等它空闲，另起一份手动模式的副本接着跑（保留对话历史，配对不变，会话 ID 会变），被拒的事不自动重做；之后需要批准的操作会停下来等你，用 `nxbridge open claude` 接入处理。新启动的后台 Claude 按上面“后台搭档全自动运行”处理。

### 检查安装

最后检查一下：

```sh
nxbridge doctor
```

`nxbridge status` 还会检查 Codex 配置里的 nxbridge 插件登记（`doctor` 输出的 `codexRegistration` 里也有）。

登记丢失（比如 Codex 配置被别的工具改写）后，新开或重新加载的 Codex 窗口就用不了 nxbridge，已经开着的窗口暂时不受影响。按提示运行 `nxbridge setup` 恢复，然后重启 Codex，并在 `/hooks` 里确认 nxbridge 的 hooks 已信任。

## 开始使用

### 发第一条消息

**只需要打开 Claude Code，不用自己开 Codex 窗口。** 在项目目录里打开 Claude，让它给 Codex 发一条消息（比如直接说“让 Codex 帮我看看这个问题”）。同一目录里没有你开着的 Codex 窗口时，nxbridge 会在后台自动启动一个 Codex 当搭档，有消息就叫醒它干活，你不用盯着它。

想看后台的 Codex 在做什么，随时可以运行 `nxbridge open codex` 接手查看，见“后台搭档”。

两边的发信方式（一般由 AI 自己调用，你只要用平常的话交代就行）：

- Claude 用 `SendMessage` 发给 `nxbridge:codex`，用 `ListAgents` 查看搭档。
- Codex 用 `claude.send_message` 发信，`claude.status` 查看搭档状态。

### 想用自己开的 Codex 窗口时

你也可以先在同一目录里自己打开 Codex，再让一边给另一边发消息。但要知道：**你自己开的 Codex 窗口空闲时不一定能被主动叫醒**。叫不醒时，Claude 发来的消息会先存着，等你在那个窗口里输入一次才会收到。

- Codex 0.166 起，直接运行 `codex` 默认使用共用后台服务（daemon）。这种窗口只有在你选择框里亲手选了它、nxbridge 又能确认它还开着时，空闲时才会被叫醒；否则只能等它自己来取消息。详见“什么时候会被主动叫醒”。
- 消息在等你自己的窗口取件时，在那个 Codex 窗口里输入 `nxbridge pickup`（或 `nxbridge 收信`）就能取到，不用随便打一句话。这句话仍会留在 Codex 的对话里，但 nxbridge 会同时告诉 Codex：这只是取信，不是在回答它的问题，也不是批准什么操作。
- 窗口已经关了的话，先在项目目录的终端运行 `codex resume <会话ID>` 重新打开同一个会话，Claude 和状态栏会给出完整命令。配对时你亲手选过这个窗口的话，重新打开后等它空闲，消息会直接送进去，不用再输入。
- 想让 Codex 收到消息就开始干活，就不要自己开 Codex 窗口，或者在下面的选择框里选“新建后台搭档”。

第一次发信时，如果同一目录下已经开着还没有搭档的另一方窗口（哪怕只有一个），Claude 会先弹出选择框：现有窗口 / 新建后台搭档 / 暂不配对。

- 只有一个现有窗口时，选项上直接写着它的名字，点一下就配上。不能被主动叫醒的窗口，选项旁会注明。
- 有好几个时，Claude 会在对话里列出各窗口的标题、状态和最近活动，问你要哪个。
- 选好后原消息自动发出。

nxbridge 不会悄悄占用你自己开的窗口；同目录没有这样的窗口时，才直接在后台启动一个。

刚打开、还没发过消息的 Codex 窗口也可以配对。你在 Codex 窗口里按 Esc 中断后，发给它的消息会等你在那个窗口继续时再送达。

### 换搭档或解除配对

在 Claude 里输入 `/nxbridge pair`（或直接跟 Claude 说“换个搭档”），在 Codex 里输入 `nxbridge pair`，会弹出同样的选择框。标题写着当前搭档，可以换成现有窗口、新建后台搭档、解除配对或保持不变。

- 换掉之前还没送到旧搭档的消息会作废，Claude 需要时会重发给新搭档；可能已经被旧搭档看到的消息不会重发。
- 分不清是哪个窗口时，按提示在目标窗口输入 `nxbridge pair <配对码>` 即可。
- 在终端里运行 `nxbridge pair` 也能按编号选择。

### 多组配对与切换对话

一台电脑上可以同时有多组配对，每个窗口只和自己的搭档通信，互不影响。

配对跟着窗口走（Codex 使用共用后台服务时例外，见下文“Codex 的共用后台服务”）：

- 在 Claude 里 `/clear`、在 Codex 里 `/new` 或切换对话，搭档都不变，对方会收到“上下文已清空”或“已切换对话”的提醒。
- 关掉窗口后用 `--resume` 打开原来的对话，会接回原来的搭档。Codex 换一种方式打开同一个对话（共用后台服务、`--no-daemon`、`nxbridge codex`）也一样；项目目录不同时会先问你。

### 窗口崩溃后接回搭档

窗口崩溃或被强制关闭后，用 `--resume` 打开原来的对话，或者在一个还没有搭档的新窗口里用 `/resume` 切回原来的对话（换了配置目录也可以）。nxbridge 确认旧窗口已经退出后会接回原来的搭档。

- 原配对已被意外解除的，会提示你恢复。
- 暂时确认不了时，消息会先保留并自动重试，仍确认不了再请你用 `nxbridge pair` 选择。
- 原来的对话还开在别的窗口里时，不会另起一个新搭档。

## 常用命令

```sh
nxbridge status      # 查看所有配对和双方状态
nxbridge pair        # 列出还没有搭档的窗口，按编号配对
nxbridge watch       # 实时查看双方的消息
nxbridge pause       # 暂停通信
nxbridge resume      # 恢复
nxbridge doctor      # 检查安装和运行状态
nxbridge doctor --current  # 在 Claude 或 Codex 里只检查本窗口的配对
nxbridge adopt codex       # 把 Codex 会话交给后台接着跑（同一会话、同一搭档）
nxbridge release codex     # 把后台 Codex 会话长期交给你自己的窗口
```

有多组配对时：

- 在 Claude 或 Codex 窗口里执行的命令，默认只作用于本窗口的配对。
- 在外部终端里执行 `pause`、`resume`、`unpair`、`restart`、`open`、`adopt`、`release` 等命令，需要用 `--pair <配对ID>`、`--member <成员ID>` 或 `--session <会话ID>` 指定目标，ID 可以从 `nxbridge status` 里查到。

## 后台搭档

同目录没有还没有搭档的另一方窗口时，nxbridge 会在后台启动 Claude 或 Codex 作为搭档。本节说明怎么查看、接手它们，以及它们掉线后怎么恢复。

### 查看和接手

想看 nxbridge 在后台启动的 Claude 或 Codex 在做什么，可以接手它：

```sh
nxbridge open claude              # Claude 空闲或在等你处理时接手
nxbridge open claude --interrupt  # Claude 正在工作时，先中断再接手
nxbridge open codex
```

接手只是临时借用：接手的窗口没连上，或你退出它之后，会话就交还给 nxbridge，之后后台掉线也会照常自动恢复。

### 后台 Codex 在等你批准操作

本版起新启动的后台 Codex 默认不需要你批准（见“后台搭档全自动运行”）。本版之前启动的后台 Codex，或者你在会话里改回了需要人批准的设置时，碰到要你批准的操作（比如执行命令、写工作区外的文件、联网）时，会停下来等你，Claude 状态栏会写“Codex 在等你批准操作”。

在这个项目目录的终端里运行 `nxbridge open codex`，就会打开原来那个会话，看到那条还在等的审批，直接选“是”或“否”。任务不会中断，也不用重跑。项目里有好几个在等时，它会按名字列出来让你选。

nxbridge 不会替你批准。

### 掉线后自动恢复

nxbridge 在后台启动的 Claude 或 Codex，不管因为什么退出（崩溃、被关掉、进程被系统结束），nxbridge 都会在几秒内发现，并按原来的会话、原来的程序和配置目录自动重新拉起。不用你手动 resume，也不会换成一个新会话。

如果这期间 Claude 或 Codex 自己更新过，会改用同一安装位置的新版本，启动前先核对确实是官方程序；你自己设置过的启动命令不会被改动。

- **重试次数：** 偶尔失败会自动再试，最多 3 次（立即、30 秒后、2 分钟后）。同一个会话每小时最多重新拉起 6 次，避免反复崩溃又反复拉起；nxbridge 自己重启也不会重新计数。
- **重试也没用的问题：** 目录没被信任、本机代理没开、找不到原来的启动配置这类问题，启动前能查出来的不占用重试次数。Claude 状态栏会写明原因和你要做的一步，消息先留着。你处理好之后，nxbridge 会在之后的正常活动中自动接着恢复。nxbridge 不会替你信任目录或改配置。
- **3 次都失败：** 配对的 AI 可以写明理由再申请试一次；再往后需要你自己处理，状态栏会给出命令。
- **恢复之后：** 恢复只让会话重新就绪，不会自动开始干活，也不会重发旧消息。如果它掉线时手上有没做完的工作，配对的 AI 会收到一条说明（在哪一轮被中断、最后在做什么），由它决定要不要让对方检查进度后继续。确定没送出过的消息照常送到，结果不明的仍然不会自动重发。
- **模型服务出故障：** 比如一直返回 503、限流、登录失效或连不上时，Claude 状态栏和 `nxbridge status` 会直接写出原因和最近一次请求的时间，例如“Codex 在等模型服务：模型服务暂时不可用（返回 503），正在自动重试，最近一次 15:28；等服务恢复，或到供应商那边查看”。这类问题只有你能处理，或者只能等服务恢复，所以 nxbridge 只说明原因：不重启进程，不建议中断，不叫 AI 去做别的，也不再因为这件事另报“hooks 没有事件”“消息还没送达”之类的连带提醒。Codex 会按它自己的设置继续重试，服务恢复后自动接着做。如果这一轮在重试用完后失败、停下了，30 秒后会叫醒配对的 AI 一次（同一轮只叫一次），状态栏也会写明原因，例如“Codex 这一轮失败：模型服务限流或额度不足（返回 429），已重试到上限”。服务直接拒绝请求本身时（例如“当前模型要求更新版本的 Codex”），通常会重复出现：状态栏会写明持续出现就需要你升级 Codex 或换用其他模型，AI 会把确切错误转告你，最多再试一次，不会反复重发。其余情况由 AI 决定是发一条简短的继续消息、自己接手，还是告诉你；限流、额度或登录这类问题通常会持续，它会先看状态，不会反复重发。Claude 这一轮失败时，也会同样叫醒 Codex。
- **提醒：** 同一次掉线只提醒一次，恢复过程中的进展只更新状态栏。
- **关闭自动恢复：** 不想让它自动恢复，就关闭那一边（见“暂时关闭某一边”）或解除配对。
- **适用范围：** 这只针对 nxbridge 自己在后台启动的会话。你自己开的窗口不会被自动拉起、关闭或接管，nxbridge 只告诉你下一步怎么做；Codex 的共用后台服务也不会被 nxbridge 停止或重启。

### Codex 会话在自己的窗口和后台之间转

一个积累了很多上下文的 Codex 会话，可以在你自己的窗口（包括 ChatGPT 应用）和 nxbridge 后台之间来回转。转来转去都是同一个会话、同一个搭档，之前的上下文和消息都在。

**交给后台：** 在系统终端（如“终端”、Windows Terminal）里运行 `nxbridge adopt codex`（或指定 `--session <会话ID>`），或者在下面说的选择框里选“在后台继续原会话”。远程连接、手边没有交互终端时，用选择框更方便。

- 会话还开在你的窗口里时，nxbridge 先记下你的选择，等你关掉窗口再转，不会替你关窗口。
- 之后你关掉窗口，会话都会自动在后台接着跑，有消息时由 nxbridge 叫醒，不再问你。
- 后台用的权限和会话原来的一样（包括你在会话里中途改过的）。读不到原来的权限时，后台先不给文件和网络权限，Claude 状态栏会写明，要放宽请按 Codex 平时的方式设置。
- 后台用这个会话原来的 Codex 程序接着跑；原来的程序更新过，就用同一安装渠道（如 Homebrew、Codex 的共用后台服务、VS Code 扩展）更新后的正式入口，不会换成别处装的 Codex。程序版本不能低于写入这个会话的版本。
- 找不到合适的程序时，会话不会被换成新的，消息也都留着。Claude 状态栏和 `nxbridge status` 会列出检查过的程序和各自的版本，并给出修法：如果是你固定的旧程序挡住了，提示取消固定（`nxbridge config unset hosts.codex.binary`）；否则提示在系统终端里运行 `nxbridge config set hosts.codex.binary <程序完整路径>`。改好配置、重新打开一次原会话，或者那个程序被更新后，nxbridge 会自动重新尝试，不用再做别的；在这之前它不会反复重试同一个注定失败的组合。

**交给自己的窗口：** 运行 `nxbridge release codex`。

- nxbridge 等后台这一轮做完（不会强行中断），确认后台进程已经退出，再告诉你可以打开，避免 Codex 提示“会话已在别处打开”。
- 之后后台不再自动拉起它；你用任意方式打开这个会话，都会接回原来的搭档。
- 已经用 `nxbridge open codex` 临时打开着的，`release` 会直接把它变成长期的，不用关掉重开。

**你自己的窗口关掉了：** 配对不会断，Claude 发的消息先存着。下次发信时会弹出选择框：在后台继续原会话 / 等我重新打开窗口 / 新建后台 Codex / 解除配对。选“等我重新打开窗口”后不再弹出；关掉选择框只是这次不选，消息留着，下次发信再问。

**会不会被叫醒：** 后台的会话有消息时会被叫醒。你自己的窗口能不能被叫醒，见下文“什么时候会被主动叫醒”；叫不醒时 Claude 会如实告诉你，你在那个窗口里输入 `nxbridge pickup` 就能取到消息。

`nxbridge open codex` 仍是临时借用：关掉窗口就交还后台。

### 在自己的窗口里打开同一个会话

后台自动恢复后，状态栏会写“已按原会话自动恢复，不用手动 resume”。如果你还是在自己的窗口里打开了同一个会话：

- 原来的后台确认已经退出、而且只有你这一个窗口在用这个会话时，直接接回原来的配对，同一会话继续。之后可以随时用 `/nxbridge pair` 换绑或解除；你关掉这个窗口后，会话会自动交还给后台，需要时由后台接着跑（用过 `release` 的除外）。
- 后台还在运行时，nxbridge 会先停止往后台送消息，再让你选用哪一个，避免同一个会话在两处同时运行。
- 没有把握时，也会让你选。

无论哪种，都不会再自动给这个窗口新建一个后台搭档；还没送到的消息只要还是同一个会话，就继续送过去。

### 关掉窗口后换一种方式打开

用 `nxbridge codex` 或装了 shell 包装后的 `codex` 打开 Codex，不管是新开、`codex resume`（带会话 ID 或从列表里选）还是分叉，默认都和官方 Codex 一样：参数原样转发，使用你当前终端的环境，目录选择和更新提示也都保留。`codex.cmd`、`codex.exe` 不经过包装，本来就是官方 Codex。

只有一种例外：你用 `codex resume <会话ID>` 打开的会话，此刻正在 nxbridge 的后台里运行（比如后台搭档），窗口会直接连到那个后台，避免同一个会话在两处运行。用 `nxbridge open codex` 查看后台搭档也是这样。这种窗口和官方窗口还有一些差别：不能用 `/cd` 和 `/worktree`，恢复时不能改权限，命令和 MCP 用的是后台启动时的环境；后台版本和你装的 Codex 不一致时会提示。退出时会告诉你怎么重新连回去。

同一个会话同一时刻只能在一处打开。关掉窗口后，会话按 Codex 自己的规则放开（用共用后台服务时 Codex 默认再等 60 秒，实际常要一两分钟；转到后台要等它放开），nxbridge 不会因为收发消息一直占着它。会话在 nxbridge 的后台里时，最后一个窗口断开、手上也没有任务后，后台会马上放开它，一般几秒后就能换 `codex resume`、`codex.cmd`、`codex --no-daemon` 或 ChatGPT 应用打开，照常接回原来的搭档。直接关掉终端窗口也一样。

如果打开时 Codex 提示 “This conversation is open in another app”，说明这个会话此刻确实还在别处使用：

- 还有别的窗口开着它：关掉那个窗口，再回来按 R。
- 它正在执行任务，或者在等你批准、回答：等这一轮结束，或者回到原来的窗口处理完。
- 它是 nxbridge 后台搭档正在运行的会话：用 `nxbridge open codex` 临时接手，或者用 `nxbridge release codex` 长期交给你自己的窗口（见上文）。
- 它在更新 nxbridge 前就在运行的旧后台里：关掉窗口后还可能再占一段时间（Codex 0.164 是 30 分钟，0.166 起是 60 秒），时间到了自动放开。更新不会停掉这些正在用的后台；之后新开的窗口都直接用官方 Codex，不会再进旧后台。

### 后台 Codex 的客户端标识

nxbridge 只负责启动和连接 Codex，干活的始终是官方 Codex 本身。所以 nxbridge 在后台启动的 Codex 发给模型服务的请求，客户端标识（User-Agent）和你直接打开的官方 Codex 一致：版本号按实际运行的 Codex 自动检测，终端信息取自你本机实际使用的终端。

## Codex 的共用后台服务

Codex 0.166 起，直接运行 `codex` 时，会话默认交给一个共用的后台服务运行，窗口只负责显示。

以下情况例外，会话仍在窗口自己的进程里运行：Windows 上以管理员权限打开、WSL 里 Codex 配置目录放在 Windows 盘上、带 `--no-daemon` 或 `--profile` 启动等。普通包装窗口和 `nxbridge codex` 默认沿用这些官方规则；是否使用共用后台由 Codex 自己决定。

nxbridge 两种情况都支持，但共用后台服务下有几点不同：

| | 共用后台服务（默认） | `codex --no-daemon` |
|---|---|---|
| 配对跟着什么走 | 会话 | 窗口 |
| 窗口内 `/new` 后 | 要重新配对 | 搭档不变 |
| 空闲时能否被主动叫醒 | 只有你亲手选的、能确认窗口还开着的会话 | 能 |
| 依赖共用服务的功能（比如 `codex agents`） | 正常 | 用不了 |

想要窗口内 `/new` 后搭档不变、空闲时也能被主动叫醒，就用 `codex --no-daemon` 打开 Codex。代价是用不了依赖共用服务的功能，比如 `codex agents`。

### 配对跟着会话走

一个共用服务同时服务多个窗口，官方接口无法确认哪个会话显示在哪个窗口里，nxbridge 不会去猜。所以配对跟着会话走，不跟着窗口走。

### `/new` 和分叉（fork）

**在 Codex 里 `/new` 后要重新配对。** 原会话被 Codex 正式结束或释放后，配对不会断，按“你自己的窗口关掉了”处理。

- Codex 默认在没有窗口使用这个会话后再等 60 秒才释放，实际常要一两分钟；如果还有别的窗口或代理在用它，会等得更久。
- 还没送达的消息会保留，不会自动转给新会话。
- Claude 下次发信时，会让你选择在后台继续原会话、等你重新打开、新建或解除配对；想改配新会话，在新会话里输入 `nxbridge pair`。

**分叉（fork）的会话：** 原会话还开着时，分叉出来的会话不会抢走原配对。原会话结束后，如果只有一个分叉会话，就由它接着原配对。

### 什么时候会被主动叫醒

**只有你亲手选的窗口、并且它还开着时，才会被主动叫醒。** 配对时你在选择框里选了这个 Codex 窗口（或用了配对码），它又正空闲、窗口也开着，消息会直接送进去，你在窗口里能看到它开始回复。“窗口还开着”要由 nxbridge 先确认：必须有一个使用共用服务、配置目录相同的 Codex 终端窗口正在运行。Linux / WSL 读取系统的进程信息；Windows 核对这个进程实际用的配置目录，以及它是否连着一个控制台窗口；macOS 核对这个终端窗口和共用服务之间的连接。确认不了就不叫醒。macOS 上的这项确认已在真机上测过：空闲的窗口几秒内就开始回复，Codex 共用服务自动升级、窗口重新连上后也一样。

这种方式有两点要注意：

- 如果你关掉了这个窗口、但还开着别的 Codex 窗口，共用后台服务在卸载前的短暂时间里仍可能让它跑一轮：结果留在那个会话的历史里，回复照常发给 Claude；需要你批准的操作会停下来等，不会自动批准。
- 如果你在这个窗口里用 `/new` 开了新对话，或者在同一个项目里又开了别的 Codex 对话，nxbridge 会认为原来那个会话可能已经没人在看，先停止叫醒它。Claude 和状态栏会点名告诉你，你可以在想用的那个对话里输入 `nxbridge pair` 重新配对，或者回原来的会话输入一次继续。消息不会自动转到新对话。

**其余情况不会被主动叫醒。** 发给它的消息会保存下来，等这个会话下一次有原生动作时取走，比如你在窗口里输入，或者它正在工作时调用工具。

- 这时消息只是存下了，还没送到。Claude 会如实告诉你，状态栏也会点名写出“有 N 条消息还没送到 Codex 窗口「…」，这个会话现在不能自动唤醒，到那个窗口输入 nxbridge pickup 即可取件”，并附上窗口已关时重新打开的命令。
- 配对时选择框也会在这类窗口旁注明这一点。
- 这样做是为了不在一个已经没人看的会话里悄悄开始工作：官方接口查不到某个会话此刻有没有窗口在看，窗口关掉后会话还会被服务保留一阵。


### nxbridge 自己启动的后台 Codex

新版 Codex 会把 nxbridge 在后台启动的 Codex 也接到共用后台服务上，这样它什么时候退出就不由 nxbridge 决定了。

- **Linux / WSL 和 Windows：** 只要你的 Codex 支持带令牌的本机连接，nxbridge 会让后台 Codex 单独运行：只在本机监听，用一个只有你的账户能读的随机令牌验证，和你自己的 Codex 互不影响，也不改你的 Codex 配置。旧版本 Codex 照旧。
- **Mac：** 后台 Codex 同样单独运行，但通过一个只有你的账户能访问的本机 socket 文件连接，还没换成带令牌的本机连接。Codex 会把这个 socket 换成一个指向系统临时目录的链接，以前的版本因此认不出这是 nxbridge 自己的后台，解除配对后停不掉，`nxbridge restart codex` 也会被拒。现在会核对链接确实指向这个进程自己正在监听的 socket，再回收或重启。这项修复还没在真机上测过。想帮忙验证的话，可以按安装包里 `tools/macos-validation.md` 第 6 节操作，验证脚本只读取信息、不调用模型，直接在安装包里就能运行，不需要源码。
- 已经在运行的后台 Codex 不会被重启，下次重新拉起时才切换。

nxbridge 不会停止、重启或更新你的共用后台服务；要中断或重开 Codex 会话，请在 Codex 窗口里操作。

## 协作中的提醒

nxbridge 会持续检查配对是否正常。发现问题时只陈述事实，交给相关的一方判断，不会自动重发消息或替谁做决定。

### 消息送不到时

对方进程退出、消息送不到时，发信的一方会自动收到提醒，恢复后也会再收到一条；不确定是否送达的消息不会被自动重发。

后续同方向的消息确认进入对方上下文后，更早的不确定投递会停止作为当前传输故障反复提醒。原消息仍保留不确定状态，随时可以按编号查阅；这不代表旧任务已经完成。

Codex 已完成取件的消息会按宿主回执确认进入上下文，不会一直停留在排队状态。

### 进度和异常提醒

**协作提醒：** 模型埋头干活久了，可能会忘了还有搭档可以分工。nxbridge 会根据实际情况判断它是不是可能忘了协作，只在这种时候提醒它，提醒的话只写在它自己的工具结果里，不会唤醒谁，也不会替它发消息。

- **什么时候提醒：** 这一方一直在干活，搭档却持续空闲，而且两边都正常（没暂停、没掉线、没在切换上下文、没有待回答的问题或送不出去的消息）。搭档在忙时不提醒，因为它可能正在做交给它的事。
- **多久提醒：** 只算真正在干活的时间，空闲、暂停、模型服务出故障或电脑休眠、后台没在运行的时间都不计。按当前的思考强度（effort）分档：xhigh / max 30 分钟，high 25 分钟，medium 20 分钟，low 及以下或判断不出时 15 分钟；没回应就按同样间隔再提醒，同一段最多 3 次。这几档以 `collaboration.sync_tip_minutes`（默认 30）为基准按比例算，设为 0 关闭所有协作提醒。
- **上下文很长时：** 上下文涨到约 40 万、60 万、85 万 token 时各提醒一次，请它重新核对搭档交代的待办和进度记录；上下文压缩只影响这一项：压缩后重新计算用量，压缩后仍然超过的档位不再提醒；压缩不会重置上面的沉默计时和提醒次数。恢复同一个对话也不会重复提醒已经提醒过的档位。
- **还没配对时：** 提醒它第一次给搭档发信就会自动配对。
- **提醒的内容：** 写明观察到的情况（比如搭档空闲多久、多久没联系），请它按 nxbridge 的默认分工、再加上你的额外要求（如有）重新分工，并允许它判断这次就该自己做。和“搭档停下、欠你回复”的提醒同时到期时合成一条，共用冷却时间，不连发。

其他提醒：

- **搭档停下、欠你回复：** 搭档停下超过 2 分钟，而你在它上次发信之后发的消息它已看过、还没回复时，提醒你一次（同一批消息只叫醒你一次，之后的提醒只记进会话），最多列出最新的 3 条（配置项 `collaboration.idle_notice_minutes`，设为 0 关闭）。
  - 搭档只要后来给你发过任何消息，更早的那些就不再列出；这只表示不再提醒，不代表那些事已经做完。
  - 只是确认或知会、本来不需要回复的新消息也可能触发，看一眼忽略即可。
- **搭档一直在忙、仍没回复：** 搭档被提醒同步后又过了一个同步周期，仍没回复你之后发的、它已看过的消息时，也会提醒你（只记进会话，不单独叫醒你），避免它在做错的事。
- **投递或进程异常：** 消息长时间没送达、一轮工作长时间看不到进展、对方进程或协调器掉线时，提醒相关的一方。
- **搭档这一轮失败、没人会接着做：** 原生重试用完后这一轮失败并停下，30 秒后叫醒另一方一次（Claude 和 Codex 都适用），不要求你之前标了要回复。唤醒 Codex 的次数用完、或者消息进了 Codex 的历史但模型 3 次都没能继续时，也会叫醒发信的一方一次：nxbridge 在后台开的 Codex，由它判断要不要再发一条简短的继续消息；你自己开的窗口，它会告诉你到原窗口继续的具体一步。还在自动重试时只显示在状态栏。你也可以自己让 nxbridge 在后台开的 Codex 接着做：在外部终端运行 `nxbridge recover codex --dry-run` 查看失败那一轮的命令，再执行给出的 `recover codex --turn <ID>`；同一轮只接受一次，模型服务本身的问题不会因此修好。
- **协调器本身停了：** 提醒平时由协调器发出，它停了也有兜底：连续 2 分钟连不上时，会叫醒一个你开着的 Claude 窗口去处理（所有窗口加起来只叫一个，nxbridge 自己在后台开的会话不算，正在更新或重启时不算；1 小时内最多叫一次，避免协调器反复崩溃时一直叫；Codex 不会被单独叫醒，要等它下次有动作时才收到这个任务），由它先运行 `nxbridge doctor` 诊断，确认协调器停了就运行一次 `nxbridge bootstrap` 把它拉起来；还是不行，它会查看日志，把原因和需要你做的一步告诉你。
- **Codex hook 超时：** Codex 的 nxbridge hook 偶尔超时不会提醒；连续多次超时、持续超过 1 分钟才会提醒，并尽量附上当时的 CPU 占用，帮你判断是机器负载高还是真的出了问题。

前台窗口也会通过原生 hooks 或 Claude 插件记录当前轮次和工具进展。Claude 插件看到模型有新输出时，只记下“有进展”的时间，不保存输出内容。普通状态查询、心跳、重试和取件不会冒充工作进展；协调器重启后保留记录，切换对话后重新开始。

### 提醒的频率和叫醒规则

提醒有频率限制：

- 问题要持续一段时间、多次确认后才发。
- 发给同一方的提醒至少间隔 1 分钟，同一类提醒至少间隔 10 分钟。
- Claude 界面会显示一行简短中文说明，具体事实在消费提醒时交给当前会话中的 AI 核验。
- 提醒在送达模型前会再核对一次，问题已经消失的不会再送。如果提醒已经排进 Claude 的队列、轮到时问题才消失，界面上会显示一行“nxbridge：这条提醒送达前问题已消失，已自动丢弃，无需处理”，忽略即可。

提醒只在 AI 真有事要做时才会叫醒它，比如欠着搭档一条回复、搭档这一轮失败后没人会接着做，或者有一步只有它能做的恢复操作。

- 只是告知的提醒（比如 nxbridge 协调器重启过、有消息投递结果不明但不会重发、另一个窗口需要你重新加载插件）不会单独叫醒空闲的 Claude 或 Codex，只记进会话，等它下次正常工作时顺带看到。
- 同一件事在 nxbridge 协调器重启后也不会重复提醒。
- 如果一条提醒排队时还需要处理、轮到时只剩告知，Claude 界面会显示一行“nxbridge：这条提醒只需告知，已附加到会话记录，未打扰 AI”，忽略即可。
- Codex 被叫醒时会在当次收到具体事实，不需要空取搭档消息；过期的唤醒会自动丢弃。
- 上下文切换提醒提交一次后也不会在每次工具调用时重复。
- 转交用户决定的问题超过原定期限后会标记超时，停止显示为待处理；不会代替用户回答或改变配对的暂停状态。

### 上下文压缩后

上下文被压缩（`/compact` 或自动压缩）后，nxbridge 会把配对和进行中的协作事实补回给模型，两边都适用。

- Codex 压缩时容易丢掉搭档发来的消息，所以压缩后还会把刚被压缩掉的那段对话里双方最后往来的 5 条消息原文（总共最多 5 万字符）直接补回去，并提醒它需要时按编号取回更早的消息。
- 补回的内容里还会列出它最后一次发信之后搭档又发来的消息编号，最多 3 条。
- Claude 这边的补回内容会作为一条消息显示在对话里，开头注明“供 AI 接续工作，你无需处理”，看到可以忽略。

### 配对被意外解除时

配对被意外解除时（比如后台服务被关停、窗口身份对不上、后台进程被回收），两边都会马上收到一条提醒，说明原因；Claude 状态栏也会一直显示，直到你处理。

下次发信时，Claude 会让你选择恢复原搭档、新建搭档或暂不配对，不会悄悄换成一个看不到之前上下文的新搭档。也可以在终端里处理：

```sh
nxbridge pair --restore <原配对ID>   # 恢复原来的配对，接回原来的会话
nxbridge unpair --session <会话ID>    # 不再需要原搭档时，清除这条提示
```

原配对 ID 写在提醒里，也能在 `nxbridge status` 里查到。你自己用 `unpair` 解除的配对不会提醒。

## 暂时关闭某一边

想让 nxbridge 暂时完全不碰某一边，可以在任一窗口里直接对 AI 说，比如在 Claude 里说“关掉 Codex”，或者在 Codex 里说“关掉 Claude”。`/nxbridge off`、`nxbridge off codex` 等同样可以由你直接关闭。

关闭后：

- 那一边的窗口照常可用，nxbridge 不再给它投递消息、不叫醒它、不重启它、不往它的上下文里补充任何内容，它那边的 nxbridge 插件也什么都不做。
- 你可以直接关掉那个窗口，nxbridge 不会在后台另起一个，也不会自动恢复或新建搭档。
- 配对和已经在排队的消息都保留；关闭期间另一边新发的消息会被直接拒收，并说明对方已关闭。
- 这个状态在窗口关闭、电脑重启后仍然保持，直到你重新打开。
- 关闭状态会显示在 Claude 状态栏和 `nxbridge status` 里。

AI 只能帮你关闭，不能替你打开。重新打开需要你亲手操作，任选其一：

- 在 Claude 输入框输入 `/nxbridge on`（打开本窗口）或 `/nxbridge on codex`（打开 Codex）；
- 在 Codex 输入框直接输入 `nxbridge on`（打开本窗口）或 `nxbridge on claude`；
- 在 Claude、Codex 之外的终端运行 `nxbridge on codex` 或 `nxbridge on claude`，有多组配对时加 `--member <成员ID>` 指定。

## 遇到问题时

### 提示需要初始化（Windows）

后台启动的搭档需要一个不随窗口关闭而退出的协调器。提示需要初始化时，运行一次 `nxbridge bootstrap`，然后重新发送消息；Claude 或 Codex 也可以替你运行。它会先确认当前环境能让协调器独立运行，确认之后才会切换，不行时什么都不改，只提示你从开始菜单打开一个普通 PowerShell 窗口再运行一次。

### 后台启动搭档失败

发信结果、`nxbridge status` 和提醒都会写明具体原因和重试方法。已经收下的消息会保留，处理好后可以重试。

新建后台 Claude 之前，nxbridge 会先检查项目目录有没有被 Claude 信任。还没信任时不会建立配对，消息先留着，并告诉你在那个目录里打开一次 `claude`、接受信任提示。

**解除配对后，后台进程一直没退出：** nxbridge 只停止它能确认是自己启动、并且没有别人在用的后台进程。确认不了时进程会留着。

- **查看：** `nxbridge doctor` 会在 `retirements` 里列出它，按当前情况标明进程还在、已退出、无法确认，或“没有已登记的可核验进程，仅剩未结算记录”，以前失败的原因单独列出。
- **回收：** 处理好原因后（比如关掉还连着它的窗口），运行 `nxbridge retire --member <成员ID>` 让 nxbridge 重新核验后回收。这条命令只回收已经解除配对、由 nxbridge 启动的成员，确认不了时照样保留进程，并在输出里列出核验了什么、哪一步没通过。
- **只剩记录：** 从来没真正启动起来的后台搭档只剩一条记录，nxbridge 不再自动反复重试。

### 新开的 Codex 窗口还没开始对话

官方接口要先有对话才能投递，所以要先在那个窗口输入一句，消息随后送达。Claude 和状态栏会这样提示你。

### Codex 的命令被沙箱或审批拦下

这一轮在 Codex 里可能仍显示“已完成”。nxbridge 会把“哪一步被拦了”告诉 Claude，但这只是工具层面的事实，任务最终是否完成以 Codex 的回复为准。

### Claude 插件没加载

只剩备用工具时，Claude 每次调用都可能弹权限确认。按提示在那个窗口执行 `/reload-plugins` 即可。

### 插件或 hooks 没有生效

插件或 hooks 没有生效时，Claude 状态栏会直接告诉你怎么处理。

AI 能自己解决的会自己择机处理：

- nxbridge 后台的 Codex 还在用旧版 hooks 或旧规则时，搭档 Claude 会等它空闲后重启它，会话 ID 和历史不变。
- hook 执行失败、没有生效或唤醒队列无法核验时，AI 会先用 `nxbridge doctor --current` 诊断，只修 nxbridge 自己的问题。
- 本窗口的 Claude 插件过期或消息回执连续失败时，Claude 会收到说明，并在一轮结束后自动重新加载一次插件（从这一版之后的更新开始生效）。

需要你做的事，比如给其他 Claude 窗口执行 /reload-plugins、在 Codex 的 /hooks 里信任、修改消息接收设置、重开你自己打开的 Codex 窗口，AI 只会告诉你具体步骤，不会替你做。

### Windows 上程序自更新后

Windows 上，Claude Code 或 Codex 自更新时可能会把正在运行的程序改名。nxbridge 会核验原进程和同目录的当前程序，核验成功后原窗口可以继续通信，后续启动也会使用当前程序。

如果当前程序缺失、无法核验，会明确提示在原窗口安全时机重开原会话；Claude 用 `/resume` 可以保留会话历史。这类宿主身份问题无法通过重新加载插件修复。

## 配置

配置文件在 `~/.nxbridge/config.toml`，需要时自己创建，nxbridge 不会改动这个文件。直接改这个文件也行：nxbridge 正在运行时会在几秒内自己读到，不用运行 `nxbridge reload`。文件没写完或写错时，继续用上一份有效的配置，改好后自动生效。

### 在 Claude 或 Codex 里修改

也可以直接在 Claude 或 Codex 里让模型帮你改：

- 普通设置（如超时、保留期限）模型可以直接改。
- 敏感设置（如启动命令、协作开关）模型只能提出改动。你需要在同一个窗口输入 `nxbridge config pending`（Claude 里是 `/nxbridge config pending`），核对差异后，输入屏幕上给出的确认行。确认码只显示给你，十分钟内有效。
- 确认后立即生效，不用再运行 `nxbridge reload`；因为配置问题停下的后台搭档会马上重新尝试。
- 在 Claude 桌面端或 VS Code 里用 Claude 时，同样在 Claude 的输入框里输入这两行。
- 如果在别的窗口里输入了查看命令，会告诉你改动是在哪个窗口提出的、还剩多长时间。

### 在终端里修改

在系统终端（比如 macOS 的“终端”、Windows Terminal）里也可以修改。在 Claude 里运行会被拒绝，包括 Claude 桌面端自带的终端面板，因为 nxbridge 没法确认那是你本人在操作。nxbridge 正在运行时，改动保存后立即生效：

```sh
nxbridge config list
nxbridge config set questions.timeout_ms 600000
```

### 指定后台启动用的命令

装了多个 Codex 或 Claude，或者平时通过 wrapper 启动它们时，可以指定后台启动用的命令，例如：

```sh
nxbridge setup --claude-command <命令> --claude-command-arg <参数>
```

参数逐个写，例如平时用 `mywrapper launch claude` 启动 Claude：

```sh
nxbridge setup --claude-command mywrapper --claude-command-arg launch --claude-command-arg claude
```

有的 wrapper 不允许 Claude 在后台单独运行：

- 在 Linux / WSL 上，nxbridge 会自动改为自己托住一个通过 wrapper 启动的 Claude，你不用另外设置。
- 在 Windows 上会提示“后台自动启动 Claude 不可用”，这时请自己先打开 Claude 窗口。

### 后台启动用的环境记录

为了让后台启动的 Claude 或 Codex 和你平时打开的一样，你正常打开窗口时，nxbridge 会把程序位置、配置目录、工作目录和环境变量记录到 `~/.nxbridge/launch-profiles.json`，后台启动时照此启动；用的是哪一份记录，会在输出里说明。

- 环境变量里可能有 API 密钥之类的敏感值。这个文件只留在本机，不会发给模型，也不会上传；它所在的 `~/.nxbridge` 目录只有你本人能访问。
- 不想用记录下来的环境，可以用上面的 `setup` 参数指定启动命令。
- `uninstall --purge` 会把它一起删除。

### 本机代理

Claude 插件通过本机 `127.0.0.1` 读取状态栏和提醒信息（只有状态和提醒编号，不含消息内容）。

如果设置了 `HTTP_PROXY` 而 `NO_PROXY` 没有包含 `127.0.0.1`，这些只读请求会经过代理；代理连不上本机时会自动改用原来的方式，不影响使用。想避免经过代理，把 `127.0.0.1` 加进 `NO_PROXY` 即可。

## 本机保存了什么

- `~/.nxbridge` 里保存双方往来的消息、问题、引用快照和压缩后补回用的摘要。这些是功能本身需要的，默认保留 7 天，并有数量和大小上限。
- 判断工作有没有进展的记录只有轮次、时间、状态和工具编号，Codex 输出只以 SHA-256 哈希的形式参与比较，不保存原文。
- 日志在运行中也有大小上限，已经结束的旧后台会话留下的文件会被清理。
- 后台启动用的环境记录见上文“后台启动用的环境记录”。

## 更新

拿到新版本的文件夹后，在这个文件夹里打开终端执行：

```sh
node nxbridge.mjs update --from .
```

这样总是由新版本自己的安装程序完成更新。从 0.1.0 更新时必须用这种方式；0.1.0 自带的 `nxbridge update` 命令会把插件清单的版本号写错。0.1.1 及以后的版本也可以直接运行 `nxbridge update --from <新版本文件夹>`。

### 更新后要做的事

更新结束时会列出这次真正需要做的事，插件内容没变的一侧不需要任何操作。通常包括：

- **Claude 插件有变化：** 已打开的 Claude 窗口执行 `/reload-plugins`。远程连接时这条命令可能用不了，nxbridge 自动重新加载也不会生效；状态栏会写明，回到电脑上执行，或者关掉窗口重新打开（`/resume` 可以回到原会话）。
- **Codex 插件有变化：**
  1. 如果 `/hooks` 里显示 nxbridge 的 hook 内容已变更，需要重新信任才会生效。同一配置目录的任意一个 Codex 窗口里确认一次即可，用了别的配置目录的 Codex 要分别确认。还没信任时，状态栏会提示去 `/hooks` 里信任。
  2. 然后新开会话，或者等 nxbridge 后台的 Codex 空闲后，在 Codex 之外的终端执行 `nxbridge restart codex`，完成前不要关闭这个终端。
  3. 信任前就已经在运行的 Codex 会话，信任后仍可能继续用旧版 hooks。这时 Claude 状态栏会提示“已信任新版 hooks，但该会话还在用旧版”：nxbridge 后台的 Codex 会由搭档 Claude 在它空闲时自动重启（也可以自己执行 `nxbridge restart codex --member <成员ID>`），你自己开的 Codex 窗口需要你重新打开会话。

更新前就开着的窗口，在按上面的方法重新加载之前，会一直用旧版本，新版本修好的问题在这些窗口里仍可能出现。所以更新后最好尽快让所有开着的窗口都重新加载一次。nxbridge 不会替你关闭或重启这些窗口。

更新时正在工作的 Codex 会话不会被打断：旧版本的插件文件会保留到确认没有 Codex 进程再用它们为止。只有更新执行的那几秒内恰好触发的 hook 可能失败一次，下一轮会自动恢复。

Windows 上如果更新结果提示“独立后台尚未启动”，再按“提示需要初始化（Windows）”的说明运行一次 `nxbridge bootstrap`。

### `/hooks` 里的 clamping 提示

Codex 0.164 和 0.166 的 `/hooks` 里可能显示 `clamping SessionEnd hook timeout to 3s`、`clamping Interrupt hook timeout to 3s`。这是正常的：Codex 对这两类 hook 最多给 3 秒，nxbridge 会在这个时间内处理完。

配置里保留原来写的 10 秒，是因为改动这个文件会让所有人更新后都得在 `/hooks` 里重新信任一次。

### 从旧版本更新的注意事项

- **0.1.0 更新到 0.1.1：** 消息记录会转换为支持多组配对的新格式，原有配对、消息和设置都会保留。这个转换是单向的：更新后不能直接装回 0.1.0 继续使用原来的记录。
- **走 HTTP 的模型服务：** 之前的版本只在 WebSocket 下可用，走 HTTP 时消息进入上下文后这一轮会报错失败，现在已经修复。
- **后台 Codex 的客户端标识：** 之前的版本会在 User-Agent 里写上 nxbridge。从旧版本更新后，已经在后台运行的 nxbridge Codex 改不了身份：nxbridge 会先暂停给它发消息，等它空闲时自动重启一次（会话和历史都保留），之后再把消息送进去，不会用旧身份发出请求。你自己打开的 Codex 窗口不受影响。
- **旧版本里接手过的会话：** 旧版本里接手过、后台又已经退出的会话，更新后能确认是接手过的会自动交还；记录已经被旧版清掉、确认不了的，会提醒你一次并给出恢复步骤。

## 卸载

```sh
nxbridge uninstall --dry-run   # 先看会做什么
nxbridge uninstall             # 卸载，保留配置和消息记录
nxbridge uninstall --purge     # 连同 ~/.nxbridge 一起删除
```

两家 CLI 自己的会话历史始终不会被删除。

nxbridge 只停止能核验由自己启动的后台进程，不会关掉你自己打开的窗口。为此，它在 `~/.nxbridge` 之外另存了一份进程归属记录，进程退出后自动删除：

- Windows：`%LOCALAPPDATA%\nxbridge\processes`
- Linux / macOS：`$XDG_STATE_HOME/nxbridge/processes`，未设置时为 `~/.local/state/nxbridge/processes`

卸载时如果还有进程没能确认退出，输出会列出进程号和记录位置，在 Claude、Codex 之外的终端重新执行 `nxbridge uninstall` 即可。
